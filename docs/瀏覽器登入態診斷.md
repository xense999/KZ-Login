# 帳號瀏覽器登入態 — 根因與修法（2026-08-18 已解決）

> **2026-08-18 結案（第二輪）：根因找到並修好，實機驗過活動頁可以正常使用。**
> 修法＝注入 `bfWebToken` 時拿掉 HttpOnly（`browser.rs` 的 `is_js_readable_cookie`）。
>
> 同日稍早的第一輪結論（「`login.beanfun.com` 的 SSO login session 被一次性消費、
> 無法重建」）**已被推翻**，記在最後一節當教訓。

## 現象（修好前）

- 網址列打 `tw.beanfun.com` → 有登入。
- 網頁點「遊戲啟動」→ 跳 `login.beanfun.com/Login/Index?pSKey=…` 的完整重新掃碼登入框。
- 活動頁 `maplestory-event.beanfun.com/Event/…` → 沒吃到登入（同一根因）。
- 剛重新掃 QR 登入後立刻測，仍跳 → 不是 session 過期。

## 兩個登入域的分工

`tw.beanfun.com/beanfun_block/bflogin/default.aspx?service=…` 現在會 302 出去：

```
302 → https://tw.newlogin.beanfun.com/checkin.aspx?skey=…&display_mode=0
302 → https://tw.newlogin.beanfun.com/checkin_step2.aspx?skey=…&display_mode=2
```

- `tw.newlogin.beanfun.com` — SSO 檢查點（checkin／check_token／把授權交還 portal）
- `login.beanfun.com` — QR 掃碼登入頁。**沒有被廢**，`checkin_step2.aspx` 裡仍寫著
  `LoginUrl = "https://login.beanfun.com/Login/Index?pSKey=" + strSessionKey;`

我們的 `get_session_key` 打 `default.aspx` 時 reqwest 會跟隨 302，最後停在
`checkin_step2.aspx` 再從最終網址抓 skey，所以 jar 裡本來就有
`tw.newlogin.beanfun.com` 的 `ASP.NET_SessionId`——新域不是沒碰到。

## 根因（已坐實）

`checkin_step2.aspx` 的 `intLoginMode = 2`，走 `DealWebToken()`，**不需要 ActiveX／NPAPI 外掛**：

```js
function DealWebToken() {
    var strWebToken = readCookie("bfWebToken");
    if (strWebToken == null || strWebToken.length < 30) {
        GotoLoginPage();                    // → document.location.href = LoginUrl
    } else {
        // POST ./generic_handlers/check_token.ashx  (web_token=1&skey=…)
        // → strAuthKey → POST tw.beanfun.com/beanfun_block/bflogin/return.aspx
    }
}
```

`readCookie` 來自該頁引用的 `scripts/cookies.js`，實作就是切 `document.cookie`。

而我們注入的 cookie 清單（`[browser] 準備注入 …` 那行 log）長這樣：

```
.beanfun.com bfWebToken |HttpOnly|Secure     ← 兇手
```

網域是對的（`.beanfun.com`，新舊登入域都送得到），但**帶著 HttpOnly＝JS 讀不到**，
`readCookie("bfWebToken")` 恆為 null → `GotoLoginPage()` → 掃碼登入框。
凡走 SSO 重授權的頁面都中；凡伺服器端自己讀 cookie 的（`tw.beanfun.com` 首頁）都正常。

## 修法

`browser.rs` `select_for_injection`：`http_only && !is_js_readable_cookie(name)`，
目前唯一的例外是 `bfWebToken`。

為什麼這不是「放寬安全性」：真瀏覽器登入後這顆一定讀得到，否則官方自己的活動頁 SSO
也會壞——所以拿掉 HttpOnly 是**還原真實登入態**。HttpOnly 只管 JS 能不能讀，
這顆 cookie 會不會隨請求送出跟它無關。

要再加例外，必須先有「哪一段網頁 JS 用 `document.cookie` 讀它」的證據，
不可以因為「注了比較保險」就整批關掉 HttpOnly。

測試：`bf_web_token_is_injected_without_http_only_so_the_sso_page_can_read_it`
（順帶：`carries_value_path_and_flags_through` 的樣本已從 `bfWebToken` 換成
`bfSecretCode`，因為前者現在是例外）。

## 教訓：第一輪為什麼判錯

第一輪只看到「SSO 走不通」就推論成「`login.beanfun.com` 的 login session 是一次性的、
被 `return.aspx` 消費掉」，並據此判定「背景保存 login session 走不通」而收工。
實際上那條路現在根本不需要 login session，只需要一顆 JS 讀得到的 `bfWebToken`。

差別在於第二輪做了兩件第一輪沒做的事：

1. **把 SSO 頁的原始碼抓下來讀**（`checkin_step2.aspx` 與它引用的 `cookies.js`），
   看清楚它到底用什麼判斷登入，而不是從外部行為反推。
2. **把注入的 cookie 旗標印出來**，而不是只印網域與名字——原本那行 log 剛好漏掉了
   唯一有鑑別力的欄位。

診斷 cookie／登入態問題時，網域對不對只是一半，**旗標（HttpOnly／Secure／SameSite）
要一起印**。
